1. Einleitung & Ziel

Dieses Projekt simuliert verteilte Systeme in einer kontrollierten Umgebung. Es werden keine echten Sockets verwendet, sondern ein kleines Framework, das Verbindungen und Nachrichtenfluss im Speicher nachbildet.

Die Aufgaben bauen aufeinander auf:

  1. A1: EchoServer – Grundlagen von Verbindung und Nachrichten.
  2. A2: ChatServer – Vergabe von Client-IDs und Weiterleitung.
  3. A3: ChatClient & Main – „echter“ Chat zwischen zwei Clients.
  4. A4: Broker-Architektur – mehrere Komponenten (Order, Payment, Shipping, IMAP) sprechen über einen Broker.

Die Zielperson kennt Java, aber kein Kotlin. Deshalb werden die Kotlin-Konzepte jeweils kurz erklärt und immer mit Java verglichen.

2. Kotlin in 5 Minuten – für Java-Entwickler

Der gesamte Code ist in Kotlin geschrieben, aber die Syntax ist Java sehr ähnlich. Hier die Features, die in diesem Projekt wirklich wichtig sind.

2.1 Funktionen & Variablen

fun add(a: Int, b: Int): Int {
    return a + b
}

// unveränderliche Variable (wie final in Java)
val maxClients: Int = 10

// veränderliche Variable (Typ wird automatisch erkannt)
var nextId = 1
  • fun: Funktionsdefinition (ähnlich int add(int a, int b) in Java).
  • val: wie final in Java (nicht veränderbar).
  • var: ganz normale veränderliche Variable.
  • Typen stehen hinter dem Namen: a: Int statt int a.

2.2 data class

data class erzeugt automatisch Constructor, toString(), equals() und hashCode(). Das entspricht grob einem POJO mit Lombok in Java: 

data class AssignId(val id: Int)
data class SendMessage(val msg: String, val toId: Int, val fromId: Int)

2.3 when – die Kotlin-Variante von switch

when (data) {
    is AssignId    -> println("ID erhalten: ${'$'}{data.id}")
    is SendMessage -> println("Nachricht: ${'$'}{data.msg}")
    else           -> println("Unbekannter Datentyp")
}
  • is AssignId entspricht grob instanceof AssignId in Java.
  • Pfeil -> bedeutet: „für diesen Fall diesen Code ausführen“.

2.4 Nullable Typen und ?

Kotlin unterscheidet strikt zwischen „darf null sein“ und „darf nicht null sein“: 

val ep1: EndPoint  // darf nicht null sein
val ep2: EndPoint? // darf null sein

Bei EndPoint? muss ich beim Zugriff vorsichtig sein, z.B.: 

ep2?.sendData("Hallo")

?. bedeutet: „nur aufrufen, wenn ep2 nicht null ist, sonst nichts tun“. Genau das benutzen wir später im ChatClient.

2.5 Funktions-Typen & Lambdas

In Kotlin kann man Typen für Funktionen schreiben, z.B.: 

(EndPoint, Any) -> Unit

Das bedeutet: „eine Funktion, die ein EndPoint und ein Any (beliebiges Objekt) bekommt und nichts zurückgibt“ (ähnlich void f(EndPoint, Object)).

Als Wert kann man dann eine Lambda-Funktion übergeben, z.B.: 

{ ep, data ->
    println("Got $data on endpoint $ep")
}

Wenn man Parameter nicht benutzt, schreibt man in Kotlin oft _ als Namen: 

{ _, _ -> }

Das ist ein leeres Lambda („mach nichts“), das zwei Parameter bekommt, sie aber ignoriert. Genau sowas verwenden wir später als Default-Wert.

3. Netzwerk-Framework: NetworkConnection.kt

3.1 Die Interfaces im Detail

interface Network {
    fun connect(address: String, handler: ConnectionHandler): EndPoint?
    fun provide(address: String, handler: ConnectionHandler): Boolean
    fun remove(address: String, handler: ConnectionHandler): Boolean
}

interface ConnectionHandler {
    fun onMsg(endPoint: EndPoint, msg: String)
    fun onData(endPoint: EndPoint, data: Any)
    fun onClose(endPoint: EndPoint)
    fun onOpen(endPoint: EndPoint)
}

interface EndPoint {
    fun sendMsg(msg: String)
    fun sendData(o: Any)
    fun close()
}

3.1.1 Interface Network

  • fun connect(address: String, handler: ConnectionHandler): EndPoint?
    – Ein Client ruft diese Methode auf, um sich zu verbinden.
    – address: z.B. "http://127.0.0.1:80/" oder "broker://local".
    – handler: Objekt, das die Callbacks (onOpen, onData, …) bekommt.
    – Rückgabewert: EndPoint? (nullable!)
        → Wenn null, gibt es keinen Server unter dieser Adresse.
        → Wenn nicht null, kann man über diesen Endpunkt senden.
  • fun provide(address: String, handler: ConnectionHandler): Boolean
    – Ein Server ruft diese Methode auf, um sich unter einer Adresse zu „registrieren“.
    – Rückgabewert: true, wenn die Adresse frei war; sonst false.
  • fun remove(address: String, handler: ConnectionHandler): Boolean
    – Meldet einen Server an einer Adresse wieder ab.
    – Wird in dieser Übung kaum genutzt, ist aber für Vollständigkeit da.

3.1.2 Interface ConnectionHandler

  • onOpen(endPoint: EndPoint) – wird aufgerufen, wenn eine neue Verbindung aufgebaut ist.
  • onClose(endPoint: EndPoint) – wird aufgerufen, wenn die Verbindung beendet wurde.
  • onMsg(endPoint: EndPoint, msg: String) – wird gerufen, wenn eine Text-Nachricht ankommt (via sendMsg).
  • onData(endPoint: EndPoint, data: Any) – wird gerufen, wenn ein Objekt ankommt (via sendData).

3.1.3 Interface EndPoint

  • sendMsg(msg: String) – Text an die andere Seite schicken.
  • sendData(o: Any) – beliebiges Objekt schicken (in der Übung meistens unsere data class-DTOs).
  • close() – Verbindung beenden.

3.2 SimpleNetwork & SimpleNetworkConnection – was passiert bei connect()?

Vereinfacht läuft der Verbindungsaufbau so ab (Pseudo-Code):

class SimpleNetwork : Network {
    private val providers = mutableMapOf<String, ConnectionHandler>()

    override fun provide(address: String, handler: ConnectionHandler): Boolean {
        if (providers.containsKey(address)) return false
        providers[address] = handler
        return true
    }

    override fun connect(address: String, handler: ConnectionHandler): EndPoint? {
        val serverHandler = providers[address] ?: return null
        val connection = SimpleNetworkConnection(handler, serverHandler)
        return connection.getClientEndPoint()
    }

    ...
}

Wenn connect() aufgerufen wird:

  1. Das Network sucht nach einem Server-Handler unter dieser Adresse.
  2. Wenn keiner vorhanden ist → null zurück.
  3. Wenn vorhanden:
    • Es wird eine SimpleNetworkConnection erzeugt.
    • Die Connection legt einen leftEndPoint (Client-Sicht) und einen rightEndPoint (Server-Sicht) an.
    • Beide Seiten bekommen ihren jeweiligen ConnectionHandler.
  4. Die Connection ruft anschließend onOpen() bei Client und Server auf.
[ Client Handler ] <-- leftEndPoint -- SimpleNetworkConnection -- rightEndPoint --> [ Server Handler ]

Dadurch können wir später das gleiche Framework sowohl für Chat als auch für den Broker verwenden.

4.1 Ziel

A1 soll zeigen, wie ein Server überhaupt Nachrichten empfängt und darauf reagiert. Dazu gibt es einen EchoServer, der Textnachrichten einfach wieder zurückschickt („echo“).

4.2 Implementierung: EchoServer.kt

class EchoServer(val sn: SimpleNetwork, val address: String) {

4.3 Erklärung wichtiger Stellen

5. Aufgabe A2 – ChatServer (IDs & Routing)

5.1 Ziel

In A2 geht es um einen ChatServer, der allen verbundenen Clients eine eindeutige ID zuweist und es erlaubt, Nachrichten gezielt an einen bestimmten Client zu senden.

5.2 Datenklassen für IDs & Nachrichten

data class AssignId(val id: Int)
data class SendMessage(val msg: String, val toId: Int, val fromId: Int)

AssignId: Wird vom Server an den Client gesendet, sobald eine Verbindung aufgebaut ist.
SendMessage: Chat-Nachricht mit Text (msg), Ziel-ID und Absender-ID.

5.3 Implementierung: ChatServer.kt

class ChatServer(sn: SimpleNetwork, address: String) {
    init {
        println("========= Start up chat server at $address ========= ")
        // Map: Client-ID -> EndPoint
        val clients: MutableMap<Int, EndPoint> = HashMap()
        // Map: EndPoint -> Client-ID (Richtung zurück)
        val endPointsToIds: MutableMap<EndPoint, Int> = HashMap()
        var freeId = 1 // nächste freie ID

        val connected = sn.provide(address, object : ConnectionHandler {

            override fun onMsg(endPoint: EndPoint, msg: String) {
                println("SERVER ($address), got msg: '$msg'")
            }

            override fun onData(endPoint: EndPoint, data: Any) {
                println("SERVER ($address), got data: '$data'")
                when (data) {
                    is SendMessage -> {
                        val toId = data.toId
                        val client = clients[toId]
                        val fromId = endPointsToIds[endPoint]
                        // Sicherheitscheck: stimmt die fromId wirklich?
                        if (fromId == data.fromId) {
                            client?.sendData(data)
                        }
                    }
                }
            }

            override fun onClose(endPoint: EndPoint) {
                println("SERVER ($address): client disconnected.")
            }

            override fun onOpen(endPoint: EndPoint) {
                println("SERVER ($address): client connected.")
                clients[freeId] = endPoint
                endPointsToIds[endPoint] = freeId
                endPoint.sendData(AssignId(freeId))
                freeId += 1
            }

        })
        if (connected) {
            println("SERVER ($address) started, listing to address $address")
        }
    }
}

5.4 Erklärung wichtiger Stellen

  • val clients: MutableMap<Int, EndPoint>
    – Key: Client-ID (Int), Value: zugehöriger EndPoint des Clients.
    – Damit kann der Server bei einer ID das passende „Kabel“ finden, um dem Client Daten zu schicken.
  • val endPointsToIds: MutableMap<EndPoint, Int>
    – Rückrichtung: EndPoint → ID. So kann der Server herausfinden, welcher Client gerade sendet.
  • override fun onOpen(endPoint: EndPoint)
    – wird vom Framework aufgerufen, wenn eine neue Verbindung kommt.
    – Hier:
    • neue ID aus freeId vergeben,
    • in beide Maps eintragen,
    • AssignId an den Client schicken.
  • override fun onData(endPoint: EndPoint, data: Any)
    – Hier verwenden wir when, um den Typ von data zu unterscheiden.
    – Im Fall is SendMessage:
    1. Ziel-ID (toId) aus dem Objekt lesen.
    2. Den Ziel-Endpunkt clients[toId] nachschlagen.
    3. Die tatsächliche Absender-ID mit endPointsToIds[endPoint] ermitteln.
    4. Nur wenn diese ID mit data.fromId übereinstimmt, wird weitergeleitet.
    5. client?.sendData(data) nutzt den Safe-Call-Operator: wenn client == null, passiert einfach nichts.

6. Aufgabe A3 – ChatClient & Main.kt

6.1 ChatClient – Überblick

Der ChatClient kapselt die gesamte Clientlogik:

  • Verbindung zum Server aufbauen (connect).
  • zugewiesene ID speichern (AssignId empfangen).
  • Chat-Nachrichten empfangen (SendMessage).
  • Chat-Nachrichten versenden (sendMessage()).

6.2 Implementierung: ChatClient.kt

class ChatClient(
    sn: SimpleNetwork,
    val name: String,
    onData: (endPoint: EndPoint, data: Any) -> Unit = { _, _ -> }
) {

    var id: Int = -1
    private val clientEndPoint: EndPoint?

    init {
        println("========= Start up client $name ========= ")
        clientEndPoint = sn.connect(address,
            object : ConnectionHandler {

                override fun onMsg(endPoint: EndPoint, msg: String) {
                    println("$name: got msg: '$msg'")
                }

                override fun onData(endPoint: EndPoint, data: Any) {
                    println("$name got data: '$data'")
                    when (data) {
                        is AssignId -> {
                            id = data.id
                            println("$name I got the id: '${'$'}{data.id}'")
                        }
                        is SendMessage -> println(
                            "$name I got the message: '${'$'}{data.msg}' " +
                            "from client with id '${'$'}{data.fromId}'"
                        )
                    }
                    // optionaler Callback, z.B. für Auto-Antworten
                    onData(endPoint, data)
                }

                override fun onClose(endPoint: EndPoint) {
                    println("$name connection on client side closed")
                }

                override fun onOpen(endPoint: EndPoint) {
                    println("$name connection established.")
                }
            })
    }

    // High-Level Chat API
    fun sendMessage(toId: Int, msg: String) {
        if (id >= 0) {
            this.sendData(SendMessage(msg, toId, id))
        }
    }

    // Low-Level API: beliebige Objekte senden
    fun sendData(data: Any) {
        clientEndPoint?.sendData(data)
    }
}

6.3 Erklärung der „komischen“ Stellen

6.3.1 Funktions-Parameter: onData: (EndPoint, Any) -> Unit = { _, _ -> }

Dieser Parameter ist ein Funktions-Typ:

  • (endPoint: EndPoint, data: Any) -> Unit bedeutet: eine Funktion, die zwei Parameter bekommt (EndPoint und Any) und nichts zurückgibt (Unit = void).
  • Der Teil = { _, _ -> } ist der Default-Wert: ein Lambda, das zwei Parameter erwartet, sie aber ignoriert (_) und nichts tut.
  • Wenn man beim Erzeugen des Clients nichts übergibt, verwendet Kotlin automatisch dieses „do nothing“-Lambda.
  • Wenn man ein eigenes Verhalten möchte (z.B. Pong-Antwort), kann man ein Lambda übergeben: 
    val c2 = ChatClient(sn, "CLIENT2") { ep, data ->
    if (data is SendMessage) {
        ep.sendData("Pong")
    }
}

6.3.2 clientEndPoint: EndPoint? und Safe-Call

private val clientEndPoint: EndPoint? bedeutet:

  • Der Endpunkt kann null sein (falls connect() fehlschlägt).
  • Im init-Block wird versucht, zu connecten: clientEndPoint = sn.connect(...).
  • Beim Senden nutzen wir den Safe-Call-Operator: 
    fun sendData(data: Any) {
    clientEndPoint?.sendData(data)
}
    – Wenn clientEndPoint == null tut der Aufruf nichts (keine Exception).
    – Wenn clientEndPoint != null, wird sendData aufgerufen.

6.3.3 object : ConnectionHandler { ... }

Das ist genau wie eine anonyme Klasse in Java: 

// Kotlin:
object : ConnectionHandler {
    override fun onOpen(...) { ... }
    ...
}

Vergleich in Java: 

new ConnectionHandler() {
    @Override public void onOpen(...) { ... }
    ...
};

6.4 main-Funktion: zwei Clients chatten

const val address: String = "http://127.0.0.1:80/"

fun main(args: Array<String>) {

    val sn = SimpleNetwork()
    val cs: ChatServer = ChatServer(sn, address)

    val c1 = ChatClient(sn, "CLIENT1")
    val c2 = ChatClient(sn, "CLIENT2") { eP, data ->
        when (data) {
            is SendMessage -> {
                // C2 antwortet automatisch mit "Pong", wenn er eine Nachricht bekommt
                eP.sendData("Pong")
            }
        }
    }

    println("========= Sending data ========= ")
    c1.sendData("Test 1")
    c2.sendData("Test 2")

    c2.sendMessage(1, "Hello, ich bin die ${'$'}{c2.id}, wer bist Du?")
    c1.sendMessage(2, "Hello, ich bin die ${'$'}{c1.id}. Wie geht es Dir?")
}

Hier sieht man den Nutzen des onData-Parameters: Client 2 bekommt ein eigenes Verhalten, ohne dass der ChatClient-Code geändert werden muss.

7. Aufgabe A4 – Broker-Architektur

7.1 Motivation

In echten Microservice-Systemen sprechen Services selten direkt miteinander. Stattdessen gibt es oft einen Broker oder Message-Bus, der Nachrichten zwischen den Komponenten vermittelt.

In dieser Aufgabe gibt es:

  • BrokerServer: zentrale Vermittlungsstelle.
  • OrderComponent: nimmt Bestellungen an.
  • PaymentComponent: simuliert Zahlungsabwicklung.
  • ShippingComponent: simuliert Versand.
  • ImapComponent: simuliert Versand von E-Mails.

7.2 Nachrichten-Typen

data class MsgRegister(val name: String)
data class PaymentRequest(val corrId: String, val account: String, val amount: Double)
data class PaymentResponse(val corrId: String, val success: Boolean)
data class ShipRequest(val corrId: String, val items: List<String>)
data class ShipResponse(val corrId: String, val success: Boolean)
data class Mail(val to: String, val subject: String, val body: String)
data class GenericForward(val to: String, val payload: Any)
  • corrId = Korrelations-ID, um zuordnen zu können, welche Antwort zu welchem Request gehört.
  • GenericForward = generischer Umschlag: „Bitte an Komponente X weiterleiten“.

7.3 BrokerServer – zentrale Vermittlung

class BrokerServer(sn: SimpleNetwork, val address: String) {

    private val components = mutableMapOf<String, EndPoint>()

    init {
        println("=== BrokerServer starting at $address ===")
        sn.provide(address, object : ConnectionHandler {

            override fun onOpen(endPoint: EndPoint) {
                println("Broker: component connected")
            }

            override fun onClose(endPoint: EndPoint) {
                val removed = components.filterValues { it == endPoint }.keys
                removed.forEach {
                    components.remove(it)
                    println("Broker: unregistered $it")
                }
            }

            override fun onMsg(endPoint: EndPoint, msg: String) {
                // Text-Nachrichten werden hier optional verarbeitet
            }

            override fun onData(endPoint: EndPoint, data: Any) {
                when (data) {

                    is MsgRegister -> {
                        components[data.name] = endPoint
                        println("Broker: registered component '${'$'}{data.name}'")
                        endPoint.sendData("REGISTERED:${'$'}{data.name}")
                    }

                    is GenericForward -> {
                        val target = data.to
                        val payload = data.payload
                        val dest = components[target]
                        if (dest != null) {
                            dest.sendData(payload)
                        } else {
                            println("Broker: Unknown target '$target' for GenericForward")
                            endPoint.sendData("ERROR:Unknown target $target")
                        }
                    }

                    is PaymentRequest -> {
                        val paymentEP = components["payment"]
                        if (paymentEP != null) {
                            println("Broker: forward PaymentRequest ${'$'}{data.corrId} to payment")
                            paymentEP.sendData(data)
                        } else {
                            println("Broker: no payment component registered")
                            endPoint.sendData(PaymentResponse(data.corrId, false))
                        }
                    }

                    is ShipRequest -> {
                        val shipEP = components["shipping"]
                        if (shipEP != null) {
                            println("Broker: forward ShipRequest ${'$'}{data.corrId} to shipping")
                            shipEP.sendData(data)
                        } else {
                            println("Broker: no shipping component")
                            endPoint.sendData(ShipResponse(data.corrId, false))
                        }
                    }

                    is Mail -> {
                        val imap = components["imap"]
                        if (imap != null) {
                            imap.sendData(data)
                        } else {
                            println("Broker: no imap registered")
                        }
                    }

                    else -> {
                        println("Broker: onData unknown type: ${'$'}{data::class.java.simpleName}")
                    }
                }
            }
        })
    }
}

7.3.1 Erklärung

  • components: MutableMap<String, EndPoint> merkt sich: Name der Komponente (z.B. "order") → deren EndPoint.
  • MsgRegister: jede Komponente sendet beim Start so eine Nachricht mit ihrem Namen → Broker speichert das.
  • GenericForward: Broker schaut data.to nach, sucht den EndPoint und leitet data.payload weiter.
  • PaymentRequest, ShipRequest, Mail sind Sonderfälle, die direkt an bestimmte Namen geroutet werden.
  • data::class.java.simpleName ist Kotlin-Reflektion und gibt den Klassennamen im Log aus („Mail“, „PaymentRequest“...).

7.4 OrderComponent – Bestellungen anstoßen

class OrderComponent(sn: SimpleNetwork, brokerAddress: String) {
    private lateinit var ep: EndPoint

    init {
        sn.connect(brokerAddress, object : ConnectionHandler {

            override fun onOpen(endPoint: EndPoint) {
                ep = endPoint
                ep.sendData(MsgRegister("order"))
            }

            override fun onMsg(endPoint: EndPoint, msg: String) {
                println("Order got msg: $msg")
            }

            override fun onData(endPoint: EndPoint, data: Any) {
                when (data) {
                    is PaymentResponse -> {
                        if (data.success) {
                            println("Order: Payment OK for ${'$'}{data.corrId}")
                            ep.sendData(
                                ShipRequest(
                                    data.corrId,
                                    listOf("items-for-${'$'}{data.corrId}")
                                )
                            )
                        } else {
                            println("Order: Payment FAILED for ${'$'}{data.corrId}")
                            ep.sendData(
                                Mail(
                                    "customer@example.com",
                                    "Payment failed",
                                    "Payment failed for order ${'$'}{data.corrId}"
                                )
                            )
                        }
                    }

                    is ShipResponse -> {
                        if (data.success) {
                            println("Order: Shipping OK for ${'$'}{data.corrId}")
                            ep.sendData(
                                Mail(
                                    "customer@example.com",
                                    "Order shipped",
                                    "Your order ${'$'}{data.corrId} has been shipped."
                                )
                            )
                        } else {
                            println("Order: Shipping FAILED for ${'$'}{data.corrId}")
                            ep.sendData(
                                Mail(
                                    "customer@example.com",
                                    "Shipping failed",
                                    "Shipping failed for order ${'$'}{data.corrId}."
                                )
                            )
                        }
                    }

                    else -> println("Order: unknown data type ${'$'}{data::class.simpleName}")
                }
            }

            override fun onClose(endPoint: EndPoint) { }
        })
    }

    fun startOrder(items: List<String>, account: String) {
        val corr = "C" + System.currentTimeMillis().toString().takeLast(5)
        println("Order: starting order $corr for account $account with items $items")
        val amount = items.size * 10.0
        ep.sendData(PaymentRequest(corr, account, amount))
    }
}

lateinit var ep: EndPoint bedeutet:

  • Die Variable wird nicht im Konstruktor initialisiert, sondern später (in onOpen).
  • „lateinit“ sagt dem Compiler: „Vertrau mir, ich setze das rechtzeitig, bevor ich es nutze.“

Ablauf: startOrder() löst PaymentRequest aus → PaymentComponent → PaymentResponse → OrderComponent → ShipRequest → ShippingComponent → ShipResponse → OrderComponent → Mail → ImapComponent.

7.5 PaymentComponent, ShippingComponent, ImapComponent

Die anderen Komponenten sind vom Pattern her sehr ähnlich: sie registrieren sich mit MsgRegister, reagieren auf bestimmte DTOs und nutzen GenericForward bzw. Mail, um wieder zum Order- oder IMAP-Service zurückzusprechen.

7.6 Demo-Programm: BrokerDemo.kt

fun main() {
    val sn = SimpleNetwork()
    val brokerAddress = "broker://local"

    val broker = BrokerServer(sn, brokerAddress)

    // Komponenten starten (sie registrieren sich beim Broker)
    val imap = ImapComponent(sn, brokerAddress)
    val payment = PaymentComponent(sn, brokerAddress)
    val shipping = ShippingComponent(sn, brokerAddress)
    val order = OrderComponent(sn, brokerAddress)

    Thread.sleep(200) // kurz warten, bis alle registriert sind
    println("=== Simulate an order now ===")
    order.startOrder(listOf("itemA", "itemB", "itemC"), "ACC-987654")
    Thread.sleep(800)
    println("=== Demo finished ===")
}

Alle Komponenten kennen nur die Adresse des Brokers. Sie sprechen niemals direkt miteinander. Das Routing übernimmt komplett die BrokerServer-Instanz.

8.3 Typische Fehlerquellen

  • Falsche Adresse beim Connect: Wenn sich ein Client mit einer Adresse verbindet, zu der kein Server registriert ist, liefert connect() null zurück. Dann ist der Endpunkt clientEndPoint null und sendData() tut nichts.
  • Vergessene Registrierung beim Broker: Wenn z.B. PaymentComponent MsgRegister("payment") nicht sendet, kann der Broker keine PaymentRequests weiterleiten.
  • IDs durcheinander: Falls ein Client Nachrichten sendet, bevor er seine AssignId bekommen hat, ist seine id noch -1 und sendMessage macht nichts.

9. Zusammenfassung

Die Abfolge von A1 bis A4 zeigt, wie man von sehr einfachen Request/Response-Beispielen zu einer kleinen Microservice-Architektur kommt:

  • A1: EchoServer – Verständnis des Verbindungslebenszyklus und der Callbacks onOpen, onMsg, onData, onClose.
  • A2/A3: ChatServer und ChatClient – ID-Vergabe, Routing von Nachrichten, Aufbau eines einfachen Chats.
  • A4: Broker-Pattern – Komponenten sind lose gekoppelt, kennen nur den Broker. Nachrichten werden über fachliche DTOs (PaymentRequest, ShipRequest, Mail, …) ausgetauscht.

Die Kombination aus simuliertem Netzwerk und Kotlin bietet eine kompakte, gut testbare Umgebung, um typische Muster verteilter Systeme zu üben – ohne die Komplexität eines echten Netzwerks.
