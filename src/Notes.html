2. Netzwerkarchitektur (NetworkConnection.kt)

2.1 Überblick

Das Framework simuliert ein echtes Netzwerk, ohne niedrige Netzwerkebene (TCP/Sockets). Stattdessen verbindet es Komponenten über zwei virtuelle Endpunkte:

  • leftEndPoint – Client
  • rightEndPoint – Server

2.2 Network-Interface

interface Network {
    fun connect(address: String, handler: ConnectionHandler): EndPoint?
    fun provide(address: String, handler: ConnectionHandler): Boolean
    fun remove(address: String, handler: ConnectionHandler): Boolean
}

provide() registriert einen Server auf einer Adresse. connect() verbindet einen Client mit dieser Adresse.

2.3 ConnectionHandler

Jede Verbindung arbeitet über diese Callbacks:

onOpen(endPoint)
onMsg(endPoint, msg: String)
onData(endPoint, data: Any)
onClose(endPoint)

2.4 EndPoint

fun sendMsg(msg: String)
fun sendData(o: Any)
fun close()

EndPoint ist das „virtuelle Kabel“ zwischen Client und Server.

2.5 Datenfluss (schematisch)

[Client Handler] <-- leftEndPoint --- rightEndPoint --> [Server Handler]

Nachrichten laufen so:

SenderZielMechanismus
ClientServerleftEndPoint.sendX → rightReceiver
ServerClientrightEndPoint.sendX → leftReceiver

Die gesamte Netzwerklogik ist robust und garantiert: Sobald beide Seiten registriert sind, ruft das System onOpen() auf.

7. Aufgabe A4 – Broker-Architektur (Ausführliche Version)

7.1 Motivation

In modernen verteilten Systemen kommunizieren Komponenten nicht direkt miteinander. Stattdessen wird ein Vermittler – ein sogenannter Message Broker – verwendet. Dieser übernimmt Aufgaben wie:

  • Routing
  • Entkopplung von Komponenten
  • Typbasierte Weiterleitung
  • Registrierung von Services

A4 simuliert diesen Aufbau vollständig.

7.2 Grundprinzip der Architektur

Alle Komponenten kennen genau eine Adresse: 


broker://local

Wichtige Regel:

Keine Komponente darf wissen, wo Payment, Shipping oder IMAP liegen. Alles geht über den Broker.

7.3 Registrierung beim Broker

Beim Aufbau einer Verbindung sendet jede Komponente:

MsgRegister("order")
MsgRegister("payment")
MsgRegister("shipping")
MsgRegister("imap")

Dadurch weiß der Broker:


components["order"]    = EndPoint(Order)
components["payment"]  = EndPoint(Payment)
components["shipping"] = EndPoint(Shipping)
components["imap"]     = EndPoint(IMAP)

7.4 Nachrichtentypen im System


data class PaymentRequest(val corrId: String, val account: String, val amount: Double)
data class PaymentResponse(val corrId: String, val success: Boolean)

data class ShipRequest(val corrId: String, val items: List)
data class ShipResponse(val corrId: String, val success: Boolean)

data class Mail(val to: String, val subject: String, val body: String)

Alle Nachrichten werden mit sendData(o) versendet.

7.5 Komponenten im Detail

OrderComponent

Bietet zentrale API: 


fun startOrder(items: List<String>, account: String)

Ablauf:

  1. Generiere Korrelation-ID
  2. Sende PaymentRequest
  3. Bei Erfolg: ShipRequest
  4. Bei Erfolg: E-Mail an Kunde (über IMAP)

PaymentComponent

Nimmt PaymentRequest entgegen, entscheidet Erfolg oder Fehlschlag.

ShippingComponent

Erstellt Versandbestätigungen.

IMAPComponent

Simuliert E-Mail-Versand.

Wenn Erfolg:

7.7 Vollständiger Ablauf (Beschreibung)

1. Der Nutzer ruft startOrder() auf. 2. Order sendet PaymentRequest. 3. Broker erkennt den Nachrichtentyp → leitet an Payment weiter. 4. Payment antwortet mit PaymentResponse. 5. Order reagiert auf Erfolg → sendet ShipRequest. 6. Broker leitet an Shipping weiter. 7. Shipping antwortet → Order verarbeitet Antwort. 8. Order sendet abschließend ein Mail-Objekt. 9. Broker leitet Mail an IMAP weiter.

7.9 Wichtige Designentscheidungen

  • Typbasierte Weiterleitung durch when (data)
  • Kein Wissensverlust: Jede Komponente kennt nur Broker
  • Flexibilität: Neue Komponenten könnten einfach hinzugefügt werden
  • Korrelation über corrId

7.10 Zusammenfassung des A4-Systems

Das A4-System bildet eine realistische, entkoppelte Microservice-Architektur nach:

  • Order orchestriert
  • Payment autorisiert
  • Shipping liefert
  • IMAP benachrichtigt
  • Broker vermittelt und entkoppelt

Damit ist ein vollständiger Bestellprozess modelliert, der sich leicht erweitern lässt.
